## 4. ผลตรวจความเสี่ยงของการ apply ลงโปรเจกต์ที่ใช้ร่วมกัน

ตรวจจาก migration 3 ไฟล์กับ seed (ไม่ได้ต่อโปรเจกต์ใดจริง) ตารางทั้งหมดอยู่ใน schema `aicp` แต่แตะของส่วนกลาง 5 จุด:

1. role ระดับ cluster `aicp_migrator`, `knowledge_runtime`: สร้างถ้ายังไม่มี ถ้ามีชื่อซ้ำจะ `ALTER ROLE` ทับ attribute
2. Storage: bucket `knowledge-originals` (private, 5 MB) ด้วย `ON CONFLICT DO UPDATE`
3. Auth: FK ไป `auth.users`, `GRANT USAGE ON SCHEMA auth` ให้ `aicp_migrator`, seed สร้างผู้ใช้สังเคราะห์ 1 คน (`@example.test`)
4. Data API: ต้อง expose schema `aicp` (setting ระดับโปรเจกต์ ต้องเพิ่มต่อท้าย ห้ามแทนที่) และ PostgREST reload schema cache
5. Pooler: ใช้ connection ร่วมของโปรเจกต์

ไม่แตะ: `CREATE EXTENSION`, schema `public`, auth settings, cron/vault เพราะโปรเจกต์ทดสอบเป็นของแยกที่รื้อทิ้งได้ ความเสี่ยงชนกับโปรดักต์อื่นจึงเกือบหมด

**Rollback (ทำมือ ยังไม่เคยลอง):** ลบ object ใน bucket แล้วลบ bucket → ลบผู้ใช้สังเคราะห์ → `DROP SCHEMA aicp CASCADE` → `REASSIGN OWNED` / `DROP ROLE` ทั้งสอง role (เฉพาะเมื่อไม่มีใครใช้) → ถอน `aicp` ออกจาก Data API โดยคงรายการอื่น หรือรื้อโปรเจกต์ทั้งก้อน
